## Recommended order with a tight deadline

Time boxes are planning limits, not guaranteed completion times. Avoid starting all of these in parallel.

1. **45–60 minutes: prove the complete user journey.** Register an entrepreneur, submit a short synthetic idea with one missing financial answer, wait for processing, answer that question, confirm the result updates, sign in as assessor, save a cited review, export, and sign out. Check that another entrepreneur cannot open it. Fix a failing step before adding features. The live clarification gap is the first target.
2. **20–30 minutes: protect the demo from connectivity and quota failures.** Confirm Atlas and one hosted processing request. Keep already processed examples available. Do not bulk-import all 55 files immediately before presenting. Use a selectable PDF when demonstrating Groq fallback; scanned PDFs still require the visual provider.
3. **30–45 minutes: manually inspect representative multilingual output.** Compare original text, translation, extracted numbers and missing questions on the approved examples. Mark uncertain output for review. This gives more useful confidence than more tests of mocked provider responses.
4. **At most 20–30 minutes: decide how to present nearby businesses.** Retry one generic public location. If services still fail, keep the unavailable state and show a separately labelled manual map/source check. Do not spend the remaining hackathon debugging several free public endpoints.
5. **15–20 minutes: rehearse the assessor decision.** Explain readiness versus risk, inspect citations, choose a next action and open the exported report. Use a known cohort if comparing cohorts.
6. **Conditional: connect the custom model only if it is a judging requirement.** Its existing weak off-topic detection is a real limitation. A hosted connection makes it usable; it does not improve its measured quality. Running new training is lower priority than a working submission-to-review flow.
7. **Reserve deployment time yourself if needed.** Test login, uploads and processing from the actual public address. No deployment has been started as part of this audit.

## Work to defer

- More cosmetic changes and additional features: the current UI and core feature set are sufficient for a focused demo.
- Training on more external rows merely to claim a larger dataset: domain mismatch and positive-only labels can reduce performance. More independent reviewed off-topic examples are more directly useful.
- Any claim of business-success prediction, calibrated financial failure probability, perfect translation or zero hallucination: there are no suitable validation labels/results to support those claims.
- Multi-server queues, shared rate-limit infrastructure and broad load testing: useful for a later production release, unnecessary for the current single-process hackathon demo.
